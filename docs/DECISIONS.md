# School Dashboard — Durable Decisions

Only established decisions belong here.

Task-local choices remain in their task Plans or implementation.

Future possibilities are not decisions.

| Decision | Established choice | Basis |
| --- | --- | --- |
| Product focus | School Dashboard is a personal academic planning application centered on helping the student answer: **What should I do today to stay on track in my classes?** | [PRODUCT_VISION.md](PRODUCT_VISION.md) |
| First milestone | Milestone 1 uses mock/hardcoded academic data in a read-only UI for one fictional student and one current term. Persistence, uploads, authentication, external research/integrations, and the future intelligence engine are excluded. | Approved product-foundation scope; [V1_SPEC.md](V1_SPEC.md) |
| Primary V1 views | Dashboard, Courses, Course Page, Weekly Plan, and Today are the five required primary views. Weekly Plan and Today must exist as dedicated views rather than only Dashboard sections. | Approved five-view UX; [V1_SPEC.md](V1_SPEC.md) |
| Course-source authority | Current instructor/current-course sources outrank historical or general sources for Course Facts. External research may enrich understanding in future workflows but must not silently replace authoritative current-course material. | Approved source-grounding principle; [PRODUCT_VISION.md](PRODUCT_VISION.md) |
| Provenance and uncertainty | Important academic information should retain its origin. Current-course facts, supplemental research, AI inference, and personal-plan suggestions must remain distinguishable. Preserve meaningful uncertainty rather than inventing certainty or unsupported numerical confidence. | Approved research-accuracy principles; [PRODUCT_VISION.md](PRODUCT_VISION.md) |
| Student approval of generated plans | Future AI-generated plans and revisions remain advisory. The student may accept, edit, reject, or request regeneration. Generated suggestions do not silently become or replace an accepted student plan. | Approved human-control principle; [PRODUCT_VISION.md](PRODUCT_VISION.md) |
| Product model boundary | Define academic concepts, relationships, and UI behavior before persistence implementation. Conceptual entities and V1 mock objects do not automatically establish production database tables, ORM models, schemas, or infrastructure. | Product-definition scope; [V1_SPEC.md](V1_SPEC.md), [ARCHITECTURE.md](ARCHITECTURE.md) |
| Initial stack | The initial application stack is Next.js, React, TypeScript, and Tailwind CSS. | [ARCHITECTURE.md](ARCHITECTURE.md) |
| Engineering workflow | Meaningful project work uses **Plan → Build → Verify** with progressive context loading. Each stage retains a separate responsibility even when one user instruction authorizes the complete task lifecycle. Human review is required only when a decision materially affects product behavior, V1 scope, durable architecture, academic semantics, security/privacy, significant dependencies, external services, destructive behavior, or another durable project choice. | Approved ICM workflow; [AGENTS.md](../AGENTS.md) and linked stage instructions |
| One-prompt task automation | One explicit instruction may authorize a single named task through its complete lifecycle: **Plan → Build → Verify → PASS → promote verified documentation → mark task Done → task-scoped commit → normal safe push**. The agent must still load and obey each stage's instructions sequentially. The authorization applies only to the named task and does not automatically authorize beginning the next roadmap task. | Approved low-ceremony task workflow; [AGENTS.md](../AGENTS.md), [../icm/01_plan/CONTEXT.md](../icm/01_plan/CONTEXT.md), [../icm/02_build/CONTEXT.md](../icm/02_build/CONTEXT.md), [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Codex autonomy | Codex and other project agents may make low-risk, reversible, task-local implementation decisions autonomously when existing project context sufficiently constrains the result. Examples include ordinary file organization, component decomposition, helper functions, local types, framework conventions, styling details, accessibility details, and small task-local refactors. These choices do not become durable project decisions merely because an agent made them. | Approved high-autonomy side-project workflow; [AGENTS.md](../AGENTS.md), [../icm/01_plan/CONTEXT.md](../icm/01_plan/CONTEXT.md), [../icm/02_build/CONTEXT.md](../icm/02_build/CONTEXT.md) |
| Plan-to-Build transition | When a task Plan reaches **READY FOR BUILD — NO MATERIAL HUMAN DECISION REQUIRED** and the active instruction authorizes the full task lifecycle, Plan proceeds directly into Build without a separate approval checkpoint. Planning-only instructions still stop after Plan. | Approved automated stage-transition rule; [../icm/01_plan/CONTEXT.md](../icm/01_plan/CONTEXT.md) |
| Build-to-Verify transition | When Build completes the accepted scope, runs proportionate Build checks, has no unresolved blocking defect, and is **READY FOR VERIFY**, it proceeds directly into Verify when the active instruction authorizes the full task lifecycle. Build does not treat its own success claims as final proof. | Approved automated stage-transition rule; [../icm/02_build/CONTEXT.md](../icm/02_build/CONTEXT.md) |
| Verify independence | Verify independently evaluates requirements against repository reality and observable evidence. Build claims and passing checks are supporting information, not automatic proof of completion. | Approved verification model; [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Verify repair authority | Verify may autonomously repair small, localized, low-risk defects when the accepted requirement is unambiguous and the repair does not change product behavior, architecture, scope, security/privacy, or another material decision. Affected checks must be rerun after the repair. | Approved Small Repair Lane; [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Current-task Git ownership | Build does **not normally commit or push unfinished current-task implementation**. The ordinary current-task flow is Build implementation → Build checks → Verify → full PASS → documentation promotion → Done → one task-scoped commit → normal push. | Approved current-task Git boundary; [AGENTS.md](../AGENTS.md), [../icm/02_build/CONTEXT.md](../icm/02_build/CONTEXT.md), [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Verified predecessor synchronization | An already-verified and already-committed predecessor task may be pushed automatically by the active agent, including Build, when the local branch is simply ahead of its configured upstream and there is no independent remote work, divergence, conflict, unrelated unsafe work, secret/private material, or destructive reconciliation required. A safe local-ahead state is not itself a blocker. | Approved non-destructive Git automation boundary; [AGENTS.md](../AGENTS.md), [../icm/02_build/CONTEXT.md](../icm/02_build/CONTEXT.md), [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Verified current-task finalization | After a task receives a **full PASS**, Verify may automatically promote justified current-state documentation, mark the task Done, stage only task-related files, create one coherent task-scoped commit, perform a normal push to the configured upstream, and confirm synchronization. No additional approval checkpoint is required for this routine non-destructive completion sequence. | Approved Git finalization workflow; [AGENTS.md](../AGENTS.md), [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| PASS threshold for automatic finalization | Ordinary automatic current-task commit and push require a **full PASS**. `PASS WITH LIMITATIONS`, `FAIL`, and `BLOCKED` do not normally receive automatic task-completion Git finalization unless an accepted task Plan explicitly defines a compatible exception. | Approved strict finalization threshold; [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Destructive Git boundary | Automatic Git authority does not include force push, `git reset --hard`, rebase, history rewriting, branch/tag deletion, discarding user work, destructive conflict resolution, overwriting genuinely divergent remote work, staging unrelated user changes, or committing/pushing secrets, credentials, or private/raw Course materials. These require explicit approval or a safe human decision when reconciliation is unclear. | Approved repository-safety boundary; [AGENTS.md](../AGENTS.md), [../icm/02_build/CONTEXT.md](../icm/02_build/CONTEXT.md), [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Failed push boundary | A failed normal push does not authorize force push, rebase, hard reset, history rewriting, or destructive reconciliation. Agents may inspect status/history and fetch safely, then stop when non-destructive resolution is unclear. | Approved Git safety rule; [AGENTS.md](../AGENTS.md), [../icm/02_build/CONTEXT.md](../icm/02_build/CONTEXT.md), [../icm/03_verify/CONTEXT.md](../icm/03_verify/CONTEXT.md) |
| Process documents remain durable | Global process documents such as `AGENTS.md`, root `CONTEXT.md`, and the Plan/Build/Verify stage contexts should remain reusable across tasks. They should not require edits after every completed roadmap item merely to record the current task. | Approved low-maintenance ICM structure; [AGENTS.md](../AGENTS.md), [CONTEXT.md](../CONTEXT.md) |
| Current project state ownership | `docs/TASKS.md` owns evolving roadmap status and sequencing. `docs/IMPLEMENTATION.md` owns verified current implementation reality. Process files may explain how to discover current state but should not be relied upon as the authoritative location for frequently changing task status. | Approved source-of-truth separation; [CONTEXT.md](../CONTEXT.md), [TASKS.md](TASKS.md), [IMPLEMENTATION.md](IMPLEMENTATION.md) |
| Documentation and task conventions | Use the durable documents routed from root `CONTEXT.md` for their assigned responsibilities and use the `SD-XXX` prefix for School Dashboard implementation tasks. | [CONTEXT.md](../CONTEXT.md), [TASKS.md](TASKS.md) |

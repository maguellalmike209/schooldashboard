# M5/M6 — Final security, quality and activation boundaries

## Distinct outcomes and status labels

**M5_IMPLEMENTATION_VERIFIED**: cutover proposal, adapter, dry-run parity/rollback and legacy contracts pass. May occur while M3 host gates remain UNKNOWN. Does not mean policy router switched.
**M5_CUTOVER_CANDIDATE**: integrated M0–M4 base and independent PR/reviewer policy verified, frozen proposal and rollback ready. A founder decision still required.
**M5_POLICY_ACTIVE**: *only* after a separate authenticated founder-approved root cutover, protected integration and explicit observation. Does not mean live writer.
**M6_OFFLINE_VERIFIED**: strict V2 envelope and child admission negative fixture tests pass, no real token or worker.
**M6_HOST_BLOCKED**: G1–G8 not proven, scheduled writer and dynamic execution DENIED.
**M6_CANARY_ELIGIBLE**: installed-host G1–G8 have fresh independently challenged proof and a specific single-task dry-run/owner grant approved; not automatically live.
**M6_LIVE_ACTIVE**: only after a separate explicit founder YES, active owner-controlled grant and real first-canary evidence. This packet does NOT authorize it.

## Eight host gates (all must be TRUE from independently verifiable evidence)

G1 — Founder-controlled external grant provenance and broker code pin/ACLs.
G2 — Native schedule request-only identity; no code, grant or GitHub bypass permission.
G3 — Worker path, secrets, network and connector denial under actual Windows token; dedicated workspace allowed.
G4 — OS exclusive lock and child-tree termination/cancellation/crash rehearsal on intended host.
G5 — Actual required CI/review, publisher branch-only rights, bypass policy and canonical-main restrictions.
G6 — Frozen acceptance with distinct independently established QA identity and hosted checks.
G7 — Externally enforced budget/reservation and observed mid-run revoke; no unlimited UNKNOWN usage.
G8 — Trusted journal, recovery-first behavior and actual-invocation/no-fiction report.

No fixture result substitutes for HOST; a GitHub branch `protected:true` summary doesn't prove reviewer/bypass roles; current integration access to protection endpoint may be 403. Never probe real secrets or change admin settings without founder approval.

## Product/business and Release invariants

Technical CI ≠ user journey, privacy compliance, legal approval or production readiness. Cross-user auth/RLS negative tests, student plan control, academic provenance, uploads/AI/provider/commercial gates and actual environment release decision retain independent ownership. No generated work may waive these by changing risk labels or acceptance. Controlled Release requires separate grant even if all milestones complete.

## Separation: two independent Master Verifies

- **M5 Master Architecture Verify:** old policy parity, new routing target, recoverable legacy unfinished state, rollback byte identity, protected Git check identity, scope of cutover, no live execution.
- **M6 Master Delegation Verify:** authority provenance, denial matrix, budget/parent/scope constraints, child admission lifecycle, recovery, revoked/expired parent, no direct worker/publisher bypass. A synthetic pass cannot be represented as authentic host PASS.

## Evidence ledger

For every assertion: exact source SHA, test command, date, environment, responsible actor/provenance, check identity and limits. Code changes invalidate affected evidence; fresh verification on final PR SHA. Avoid PASS based on reviewed test names rather than executed checks. Include a redacted one-page management summary and linked detailed artifacts.
